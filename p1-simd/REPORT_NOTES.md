# REPORT_NOTES (sanity runs only; NOT final data - QUICK config, 3 samples, shared machine, core 3)

All numbers below are from `data/raw/sanity` (tiny runs). Re-collect under bench mode before using any number in the report.

## What the sanity runs showed
* Correctness checks pass for all 4 kernels x f32/f64/i32 x unit/stride(1,2,4,8)/gather(perm,block) x scalar/sse/avx2/znver5/znver5_fm (n=1000,1003 plus run configs).
* Effective core clock (perf cycles / ns) ~5.4-5.6 GHz, slightly lower under zmm FMA load (5.43-5.55). TSC would not equal this.
* peakflops: fp32 zmm 63.98 FLOP/cycle (353.7 GFLOP/s @5.53 GHz) => 2 x 512-bit FMA/cycle confirmed; ymm 31.99, xmm 15.99, fp64 zmm 31.99.
  (First version compiled at -O2 kept accumulators in memory and gave 19 FLOP/cycle: needed -O3 + unroll. Beware if rewriting.)
* membw single-thread read (sanity): ~625 GiB/s at 16 KiB (L1), ~200 GiB/s at 1 MiB (L2), ~75 GiB/s at 64 MiB, ~51-57 GiB/s at 256 MiB (DRAM); triad ~30 GiB/s at DRAM sizes (counts 3 arrays, no write-allocate).
* Speedup over scalar, f32, saxpy: 16 KiB footprint: SSE2 3.4-3.6x, AVX2 6.2x, znver5 9.9-11x; 128 MiB (DRAM): 1.04x-1.7x depending on the
  run. Reviewer re-runs (11 samples, several invocations): vector builds all ~3.6-3.7 ms (~49-51 GiB/s algorithmic, equal for all widths),
  but *scalar* saxpy at 128 MiB varies 4.1-6.2 ms BETWEEN processes (<1% within a process) => the DRAM speedup is 1.1-1.7x and must be
  reported from pooled REPEATS (now default 3), not from one invocation.
  stencil: 16 KiB 3.6x / 6.4x / 9.6x; 128 MiB: the earlier "AVX2 0.82x" did NOT reproduce: 2 invocations x 11 samples gave
  sse 1.29-1.40x, avx2 1.33-1.44x, znver5 1.42-1.45x. Scalar stencil is compute-bound even at DRAM (3 mulss/elem on 2 FMUL pipes:
  1.67-1.70 cyc/elem at every size, 24 GiB/s), which is why the stencil keeps ~1.4x at DRAM while saxpy/mul do not.
  multiply: 16 KiB 3.3x / 5.5x / 9.9-10.2x; DRAM ~1.1x (truly memory bound, scalar ~2.0 cyc/elem at DRAM vs 1.03 in L1).
* scalar_znver5 control (no-vec, -march=znver5, scalar FMA): saxpy 1.045 cyc/elem (= scalar), stencil 1.51 (vs 1.68) at 16 KiB =>
  speedups are SIMD width, not FMA.
* dot (non-fast-math): speedup 0.88-1.02x for sse/avx2/znver5 at every size (negative example, see below); with `-fassociative-math` (znver5_fm): 28.8x at 16 KiB, 2.6x at 128 MiB.
* Scalar dot costs ~2 cycles/element (loop-carried add latency chain), scalar saxpy ~1 cycle/element.
* Alignment (16 KiB, saxpy f32, reviewer re-run 11 samples): znver5 0.0997 cyc/elem aligned vs 0.133 at +4 B and 0.134 at +32 B (every
  64 B zmm load/store splits two lines; GCC does not peel for alignment, it uses unaligned vmovups + a masked epilogue); avx2 0.168 aligned,
  0.208 at +4 B, 0.168 at +32 B (a 32 B ymm access at offset 32 never splits) ; scalar flat 1.045. +64 B offset == aligned (control).
* Stride (saxpy f32, L1): znver5 0.10 cyc/elem unit -> ~0.58 at stride 2 -> ~0.8 stride 8 -> ~1.0 gather; scalar ~1.05-1.3 flat. Vector advantage shrinks to ~1x at stride>=8/gather and DRAM sizes.
* Strided / gather dot without fast-math stays ~2 cyc/elem in all builds (serial reduction), znver5_fm vectorizes it.

## Vectorization status (from reports/vec_summary.md, objdump ground truth; type f32)
* scalar: all kernels scalar (empty opt-info report).
* sse: saxpy/mul/stencil/strided-saxpy/gather-saxpy vectorized, 128-bit (xmm), no FMA; dot = "partial" (see below); dot_gather scalar.
* avx2: unit-stride kernels ymm + vfmadd; saxpy_gather xmm+fma (index loads assembled with vinsertps, no vgather).
* znver5: saxpy/mul/stencil/stride-saxpy zmm (+vfmadd, masked epilogue); gather saxpy xmm; dot partial; dot_gather scalar.
* znver5_pv512: generated code identical to znver5 => `-mprefer-vector-width=512` NOT needed with GCC 16.2 for znver5.
* *_fm: dot becomes a true vector reduction (zmm, 4 accumulators, vfmadd231ps); dot_gather xmm/zmm-less (gather loads assembled).
* i32: all unit-stride kernels vectorized in every vector build (int reduction needs no fast-math).

## Surprises / things to mention in the report
* GCC prints "loop vectorized" for the non-fast-math FP dot, but the loop only vectorizes the multiplies: after `vmulps zmm` it extracts each lane
  and does a chain of scalar `vaddss` (in-order reduction preserved). So the opt-info message alone is misleading; the objdump (`reports/vec_snippets.md`)
  shows serial adds => no speedup. This is the negative example (and why objdump is the ground truth in `vec_check.py`).
* No vgather instructions were generated by GCC for znver5 even for the gather kernels.
* The sanity DRAM points have large variance (QUICK: K=1, 3 samples, 1 invocation); real runs use 15 samples x 3 invocations.
* Sanity runs were taken while other projects (P2 bandwidth runs on cpus 4-11 = same CCD/L3/memory controller as cpu 3; P3 fio) were
  active: DRAM/L3 numbers here are contaminated. Final collection needs an otherwise idle machine.
* Roofline arithmetic intensities are tiny (<=0.63 FLOP/B) so every kernel is left of the ridge point at DRAM; L1-resident points exceed the DRAM roof and approach the L1/L2 bandwidth roofs.
